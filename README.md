# plugin-link

A generic [LinkML](https://linkml.io/) ERD viewer built with [SvelteKit](https://svelte.dev/docs/kit) and [Svelte Flow](https://svelteflow.dev/).

Upload any LinkML schema YAML file and explore it as an interactive entity-relationship diagram. Nodes are collapsible table cards; FK and ETL edges are the relationships reconciled off-client by the single LinkML producer.

Defaults to the fully merged [OMOP CDM](https://ohdsi.github.io/CommonDataModel/) v5.4 schema (37 classes with 42 foreign-key edges). Also includes the **SEIN** schema — a merged HiX staging + OMOP CDM subset with slot-level ETL mappings.

The app ships in three forms from the same SvelteKit frontend: a **static web build** (GitHub Pages), a **served web build** (`deploy/serve.mjs` under launchd, which also exposes the upload boundary), and a **native desktop app** built with [Tauri v2](https://tauri.app).

## Semantic authority — one producer, native pipeline

There is exactly one LinkML implementation: `produce.py` (pinned Python `linkml` 1.11.1 + `SchemaView`), invoked by the **native Vite pipeline** (`vite.config.ts`). It runs **off-client** and emits a deterministic JSON artefact. The browser never parses LinkML.

| Input mode | Path |
|---|---|
| **Bundled** | `static/reconciled/<name>.json` — generated by the Vite plugin on dev-server start and on build, then fetched and projected into the viewer |
| **Uploaded / hand-edited** | `POST /reconcile` — served by the Vite plugin's native dev-server middleware, running the *same* `produce.py`, returning the *same* artefact shape |

The bundled schemas are a pipeline output, not a hand-committed artefact set. Uploads and live editor edits are served off-client by the Vite plugin (`/reconcile`) in dev and by the served production origin (`deploy/serve.mjs`) in production. A static-only deployment (GitHub Pages, Tauri) serves the bundled schemas but has no reconcile endpoint, so uploads there require `VITE_RECONCILE_URL` pointing at a served origin. There is no in-browser fallback in any mode.

The producer environment is a **locked uv project** committed in the repository: `pyproject.toml` (declares `linkml==1.11.1`), `uv.lock` (exact resolved dependency set) and `.python-version` (`3.12`). Every boundary — build, dev middleware, production origin and the offline verifier — invokes it as `uv run --locked produce.py …`, where `--locked` refuses to run against a missing or stale lock. The reconciled artefacts land in `static/reconciled/`.

### Reproducibility contract

```
identical repository source state
  + identical locked producer environment
  -> identical reconciled content (reproducibility.content_digest)
```

Each artefact records two digests plus toolchain provenance:

| Field | Meaning |
|---|---|
| `reproducibility.content_digest` | Content identity: source + projection rules, **independent** of the Python/linkml toolchain. |
| `reproducibility.output_digest` | Content identity **+** toolchain provenance. |
| `reproducibility.{python_version, linkml_version, linkml_runtime_version}` | Which locked environment produced this artefact. |

The toolchain metadata is kept deliberately: it tells you *which* environment produced an artefact rather than being the only reason two otherwise identical artefacts differ. The clean-environment proof is `bun run test:repro`, which runs the producer twice, each pass in its own freshly-synced environment from `uv.lock`, and requires byte-identical output with equal content and output digests.

### Build, dev, and preview timing

- **`bun run build`** — `buildStart` *awaits* the producer before the bundle is emitted, so a producer failure fails the build with its own error and every `static/reconciled/*.json` artefact exists before `static/` is copied.
- **`bun run dev`** — generation is started off the critical path (dev-server availability does not wait on a cold `uv` toolchain provision); the viewer's artefact fetch retries (dev only, bounded) until the output is written.
- **`bun run preview`** — serves the already-built output. It deliberately mirrors the production static export: no generation and no `/reconcile` endpoint. A missing `build/reconciled/` produces a clear warning; the fix is to rebuild.

### Deployment matrix (authoritative)

There are two production shapes and two local shapes. The bundled viewer is always static; only the upload/edit reconcile boundary depends on a server.

| Mode | Bundled viewer (static) | Upload / hand-edited reconcile | Reconciliation executed by | Base path |
|---|---|---|---|---|
| **Production — served origin** (`deploy/serve.mjs` under launchd `com.semiac.linkml-viewer`, Cloudflare ingress `/linkml-viewer/*`) | yes | yes — `POST /linkml-viewer/reconcile` | the same `produce.py` via `deploy/producer-runner.mjs` | `/linkml-viewer` (`BASE_PATH`) |
| **Production — static export** (GitHub Pages via `.github/workflows/deploy.yml`) | yes | **no** — no server hook; requires `VITE_RECONCILE_URL` pointing at a served origin | none (artefacts baked at build) | `/plugin-link` (default) |
| **Desktop** (Tauri v2) | yes | no in-app server; requires `VITE_RECONCILE_URL` for uploads | none | empty |
| **Vite dev** (`bun run dev`) | yes (generated off the critical path) | yes — `POST /reconcile` middleware in `vite.config.ts` | the same `produce.py` via `deploy/producer-runner.mjs` | empty |
| **Vite preview** (`bun run preview`) | yes (prebuilt) | no (mirrors the static export) | none | empty |

`VITE_RECONCILE_URL` defaults to the app's own `base`, so the served origin's same-origin boundary is correct without configuration. There is no in-browser LinkML path and no fallback: if the configured boundary is unreachable, the caller surfaces an error.

## Desktop (Tauri v2)

The same SvelteKit frontend is wrapped in a native window via Tauri v2. Supports macOS, Windows, and Linux.

### Development

```sh
just dev-tauri     # or: bun run tauri:dev
```

Starts the Vite dev server and opens the app in a native window.

### Building

```sh
just build-tauri              # build for the current platform
just build-macos-silicon      # macOS Apple Silicon .app + .dmg
                              # prerequisite: brew install create-dmg
```

Output artifacts are placed in `src-tauri/target/<target-triple>/release/bundle/`.

## Features

- Drag-and-drop upload of any `.yaml` / `.yml` LinkML schema (reconciled through the producer service)
- **Schema YAML editor** — live CodeMirror 6 editor with syntax highlighting; edits are validated for YAML syntax and re-reconciled through the producer service (500ms debounce). It does not parse LinkML in the browser.
- **In-browser group color editor** — edit group labels and colors live without touching any files
- Auto-layout via [Dagre](https://github.com/dagrejs/dagre) or [ELK](https://eclipse.dev/elk/) (layered algorithm), switchable at runtime — controls are labelled by intent (*Left → Right* / *Top → Bottom*) with the engine (*ELK* / *Dagre*) as a secondary axis
- Left-side **group legend** sidebar — shown automatically when the schema has group-annotated classes; lists color swatches, slot row icon key, and edge type legend
- **Group-colored node headers** — each class's header is colored by its group annotation (configured in `static/group-config.yaml`)
- **ETL mapping badges** — slots with `exact_mappings` show the target column as an indigo italic badge, with the full mapping list on hover
- **ETL edges** — dashed indigo arrows drawn to the mapping's named target column (e.g. HiX → OMOP)
- Collapsible table nodes (click the chevron in the header); clicking the header itself selects the table
- **Selection semantics** — the chosen table/row is *selected*, its neighbours *related*, the rest *dimmed*; collapse (the chevron) is a distinct affordance and never changes the selection
- **Relationship labels** — the inspected (selected/hovered) relationship shows its slot name at a stable screen size; below LOD2 the full static label set is suppressed
- **Examples menu** — switch between the bundled example schemas (OMOP CDM, SEIN) with a LinkML → ERD vocabulary note: *Class → Table · Slot → Column · Range → related table*
- Top-bar search with keyboard navigation and canvas pan-to-node
- MiniMap with group-aware node coloring

## Groups

Classes in a LinkML schema can carry a `group` annotation. When present, the node header is colored according to the group's entry in `static/group-config.yaml`, and the **group legend** sidebar appears automatically.

`annotations.group` is the canonical annotation. There is no `domain` alias — a `domain` annotation is ignored by the viewer.

### Annotating a class

Use the **compact annotation form** (a plain scalar value):

```yaml
classes:
  Person:
    annotations:
      group: clinical
    attributes:
      person_id:
        identifier: true
```

The LinkML metamodel also allows an expanded `{tag, value}` form, but the compact form is preferred and is what the included schemas (`sein.yaml`, `hix.yaml`) use:

```yaml
# expanded form — verbose, avoid
annotations:
  group:
    tag: group
    value: clinical
```

The parser accepts both forms.

### Configuring group colors

Edit `static/group-config.yaml` to add or change groups — no TypeScript changes required:

```yaml
groups:
  - name: clinical
    label: Clinical
    color: "#2563eb"
    text_color: "#ffffff"
  - name: hix
    label: HiX Source
    color: "#f59e0b"
    text_color: "#ffffff"
  - name: default
    label: Other
    color: "#475569"
    text_color: "#ffffff"
```

The `default` entry is the fallback color for classes whose group value does not match any named entry. It is not shown in the legend swatch list.

## ETL mappings

Slots can declare `exact_mappings` to record cross-schema column mappings (e.g. from a HiX staging column to an OMOP CDM column):

```yaml
attributes:
  patient_number:
    exact_mappings:
      - omop_cdm54:Person.person_source_value
```

The first mapping is shown as an indigo italic badge in the slot row (prefix stripped). Hover over it to see all mappings.

When both source and target classes are present in the schema, a **dashed indigo ETL edge** is drawn between them on the canvas.

## In-browser editors

Two slide-in panels are accessible from the top bar:

- **`</> Schema`** — opens a CodeMirror 6 YAML editor pre-loaded with the current schema. Edits are validated for YAML syntax (500ms debounce); valid text replaces the active workspace file and is re-reconciled through the producer service. Parse errors are shown in a red bar; the canvas is not updated until the YAML is valid.
- **`◎ Groups`** — opens a group color-picker form. Each row has a name, label, background color, and text color. Changes are applied to all node headers and the legend immediately.
